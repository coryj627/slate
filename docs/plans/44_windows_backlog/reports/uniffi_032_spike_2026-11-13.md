# WB-32: the uniffi 0.32 spike, 2026-11-13

Plan 44 WB-32 (`specs/wb32_uniffi_032_spike.md`), for #998. Run on the
owner's Windows desktop, in one PowerShell session, on the branch
`claude/wb32-uniffi-032-spike` cut from `main` at `0e71073a`, with
`CARGO_TARGET_DIR=C:\dev\slate\target-wb32`.

**Result:** the bump needs no source change on either side of the FFI.
The C# binding's public surface is unchanged, and every suite passes on
it.

## What changed since the spec

- **The generator has a tag.** NordSecurity/uniffi-bindgen-cs released
  `v0.12.0+v0.32.0` on 2026-11-09 (commit `fc32e9bb`). The spike used the
  tag rather than the fork's PR #176 head.
- **Its cooldown.** The tag was four days old on the spike's date. The
  owner gave the bump a cooldown exception for this tag on 2026-11-13,
  so the bump lands now rather than on or after 2026-11-16.
- **The pin moved.** The repository's pin is `v0.11.1+v0.31.0` (#1538),
  not the spec's `v0.11.0+v0.31.0`.

  - C#: `slate_uniffi.cs` (2,026,164 bytes);
  - Swift, from the same 0.31 DLL: `slate_uniffi.swift` (1,367,783 bytes),

## Step 4: the generated C#

Regenerated through `generate-bindings.ps1 -Locked` with the 0.32
generator first on `PATH`, into an emptied directory: `slate_uniffi.cs`
is 2,026,926 bytes.

- 1,491 lines changed. 1,460 are checksum constants.
- **Public symbols:** none removed or renamed. The two lines only after
  the bump are members of a new `internal` struct, `ForeignBytesPin`.
  The generator uses it to pin a `byte[]` for a `&[u8]` argument instead
  of copying it into a `RustBuffer`. Slate's FFI passes no such argument
  today.
- **Everything else** is the header's generator version and the
  `ForeignBytes` comment.
- **No C# analogue of Swift's `indirect` enums:** `EmbedResolution` and
  `PropertyValue` were already `public record` hierarchies, reference
  types that can contain themselves.

No census needs extending: no symbol a census could have missed changed.

## Step 6: the Swift binding

From the 0.32 DLL with the workspace's own `uniffi-bindgen` bin:

- **`slate_uniffiFFI.h` and `slate_uniffiFFI.modulemap`:**
  byte-identical, as #998 said.
- **`slate_uniffi.swift`:** 2,112 lines changed.
  - 730 are checksums.
  - 1,095 rename the call-status closure argument from `$0` to
    `uniffiCallStatus`.
  - `EmbedResolution` and `PropertyValue` become `public indirect enum`,
    as #998 said. They are the two enums that contain themselves. The 58
    "we don't yet support `indirect`" comments go.
  - The error enums' `public` moves onto a line of its own. swift-format
    is not installed here, and the Mac build formats or ignores it.
  - A new `fileprivate` converter, `FfiConverterByRefBytes`, for `&[u8]`
    arguments.
- **Public declarations:** 1,457 before and after.

`indirect` changes neither how a case is built nor how it is matched, so
no Swift source change is expected. Whether `swift build` and the Mac
tests pass is the Mac lane's to show on the bump PR.

## The askama and Namespace cache exposure

#998's second blocker was askama 0.16's derive. It reads `askama.toml`
through a canonical path and emits it relative to a non-canonical one.
It failed on a Namespace **mac** runner whose `~/.cargo` resolved
through `/Volumes/cache`.

Today no mac lane uses `cache: rust`: `swift-tests.yml` has no `cache:`
line, and the mac lanes run on the Studio. These do use it:
- `rust.yml`'s lint, test and bench-compile jobs (Linux arm64 Namespace);
- `nightly.yml`;
- five `windows.yml` jobs on Windows Namespace runners.

Whether their cache mounts make the two paths disagree shows only on CI.
The bump PR's first lane run is that check. If one fails at
`uniffi_bindgen`'s `#[derive(Template)]`, the workaround is #998's: set
`CARGO_HOME` to the real path in that job.

## What the bump needs

1. `Cargo.toml`: `uniffi = { version = "0.32", features = ["cli"] }`.
2. `Cargo.lock`: step 3's update.
3. `apps/slate-windows/uniffi-bindgen-cs.version`: `v0.12.0+v0.32.0`. The
   lanes' regex accepts it, so no interim fork pin is needed, and the
   owner question the spec raised falls away.
4. `ci/windows-runner/golden/versions.json`'s `bindgenTag`, which
   `Golden.Tests.ps1` holds equal to the version file, and
   `CONTRIBUTING.md`'s install line.
5. **Owner steps:**
   - the home golden image preinstalls the old tag, so the next golden
     rebuild picks up the new one. Until then a home job installs it
     itself, as the lanes do on a cache miss;
   - each developer machine reinstalls the generator.
6. No source edit, on either side.
7. The lanes' generator cache is keyed by the tag, so it turns over by
   itself.

**Estimate:** the bump PR is these edits plus one lane run.
