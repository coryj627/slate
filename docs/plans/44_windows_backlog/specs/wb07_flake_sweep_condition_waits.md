## Amended at implementation (2026-10-27)

This section outranks the text below it.

- **Drift from main at b13e5048:**
  - **The STA timeout path grew a stack and a dump** (#1603, #1641): on a missed join it takes the body's stack on its dispatcher, writes a dump when it could not, and only then shuts the dispatcher down. The token is cancelled after the stack and the dump, so a body that stops on its token has not left before either is taken.
  - **The fact's name comes from xUnit, not from `[CallerMemberName]`.** About eighty per-class helpers forward to `StaThread.Run`, so a caller-member name would name the helper. `Run` reads `TestContext.Current.Test.TestDisplayName` on the calling thread, so every run names its fact, theory rows included. `Run` takes no `factName` parameter, and `StaThreadCensus` gains no rule for one.
  - **The unsaved-changes prompt fact has no 5 s wait.** The close is synchronous, so pumping until `duringPrompt` is set cannot help. #1323's run failed because the close refused before its prompt: at aaa93f8b a close with a files-tree read in flight was refused at once, and since XB-11 it waits only 5 s (`TreeRefreshCloseBound`) for that read. The fact now pumps, with a 30 s bound, until the sidebar has no tree read or child load in flight, no debounced sidebar refresh is pending (one would start a read without a pump) and the lifecycle is not busy. It settles before it parks the lane item, so the two waits share no bound, and from the settle to the close nothing pumps. If the close still refuses, the failure names the refusal it announced.
  - **`OpenCanvasFromTree` waits for the files tree (30 s) and then selects through the gate's `SelectTreeItem`.** That helper finds the row again on every attempt, selects it, checks the selection holds, and retries a transient UIA fault. A publication can replace the row's element between a lookup and its select (Codex round 2). No new `SpinUntil` is written.
  - **#1612's `WaitForTreeItemStartingWith` builds its failure message only once the wait has failed, and best-effort.** Its message used to read the group's name, expansion and descendants eagerly, even after a successful wait, so one transient fault there failed a call whose row was present (Codex round 2).
- **`ReleaseProjection` was not already fixed.** The spec expected it was, but #1323 is right. `LetTheHeldFetchRunOut` waits for the latest operation posted from ANY other thread, so another worker's post could end the wait before the released projection's own. The fixture now marks the fetch's flow at its fault seam, with an `AsyncLocal` holding the gate it passed. The value flows with the fetch's execution context across the retry's await, and the post hook runs on the posting thread inside the poster's flow. The wait takes only the first post made in that flow past the gate: its publish, its terminal failure, or its cancellation. Another thread's post, and unrelated work on the fetch's own pool thread, are both skipped. Every way an asynchronous fetch ends makes exactly one post in its flow: its publish, its terminal failure, a rescan's cancellation, or its retirement's settling of its waiters. Each end of the release therefore waits for that post to have run. A retirement also counts, but the count moves one statement before its post. Codex round 2: the retired and cleanup ends trusted the count alone.
  - **Not deterministic:** a regression for "the count moved, the post has not". No seam sits between those two product statements.
  - **Filed as #1673:** the fixture's `Dispose` releasing a gate that no fetch has reached yet, without waiting. This is pre-existing, outside #1323's item. Codex round 1 showed that a pool-thread identity fails both ways: the thread can run other work while the fetch awaits its retry delay, and a cancellation can resume on a thread that never passed the seam. The 20 call sites keep their meaning. New facts:
  - `TheReleaseWaitsForItsOwnProjectionNotAnotherPost` is a theory with two posters, another thread (its flow suppressed) and the fetch's own thread under a context captured outside the fetch. Each post runs while the released fetch is still fetching, and the release must still return with the projection shown.
  - `TheReleaseFollowsItsFetchThroughATransientRetry` fails the first attempt with a transient read error. The release follows the retried fetch to its publish.
- **The graph probes park the replacing fetch.** This is the design's second option. Capturing the token inside the predicate can miss a replacing pair that is issued, published and cleared within one drain. `Park` now takes the fetch numbers to hold, for example `new Park(document, 1, 2)`, plus `WaitParked(n)`. The token is read while its fetch is held. The sort fact holds fetches 1 and 3: its rows fetch (2) must land for the receiver to issue the pair. The audit found the same pump-then-read race in two more facts, `AProbesPairInheritsThePendingSortAndAdoptsItWithGridSortedThenTheCount` and `AProbeDuringASilentTokenIsSilent`, so six facts read a held token now. The other reads follow a synchronous `Request` with no pumping, so the publication cannot run before them. The park's self-release is now 30 s, not 10 s. `Release` waits until every entered park has recorded its outcome and resumed, then fails if any ran out. Codex round 1: a worker that timed out could otherwise record it after the check. `Dispose` only sets the release, leaving the events to the collector (the diagram park's rule), because a parked pool thread may still be waking.
- **The highlight census's helper waits for the debounce too.** `PumpUntilRefreshed` waits until the count has passed the baseline and the coordinator's debounce timer is idle. The next step's baseline is then read after this step's refresh, so a leftover refresh cannot pass a later step. The show step (`:171`) uses the helper as well, after its 200 ms settle.

  - **There is no inflight directory.** A batch's durable intent lives in the cache's `structural_batch_inflight` and `_rewrites` tables, so the "inflight listing" is those rows, read on a connection of their own. A `from_filesystem` session has no fault-injecting provider, and its context says the calls were not recorded.

The in-process waits block in `VaultStructuralLock::acquire`'s registry wait, which has no seam. Each blocked thread therefore signals immediately before its call, which proves the thread is running and about to block, not that it is inside the wait. - **A wedged body whose thread started late stays tracked.** This gap predates WB-7 (Codex round 1). A fact's thread that had not yet recorded its OS exit handle when both joins expired was entered with a null exit, which `Wedged()` read as ended: it reported the body as residue once and then forgot it. The entry now keeps the thread and reads its exit when asked. While no exit is recorded, the body counts as running for as long as the thread is alive. `StaThread.BeforeBodyForTests` delays a body's first line, and `AWedgedBodyWhoseThreadStartedLateIsStillTracked` uses it. A dead thread with no exit on the first read has its exit read again before it is forgotten, because a late-started body can record its exit and end between the two reads (Codex round 4). That interleaving has no deterministic regression: it would need a pause inside `Wedged()` between its reads.
- **The StaThread facts start their bound once the body runs.** `TheTokenABodyReadsIsTheOneItsRunCancels` and the wedge helper hold the join (`AfterStartForTests`) until the body has read its token, so a thread that first runs late cannot fail the premise or leave the body untracked. The token fact's body then polls its token until it is cancelled, under a 30 s cap, instead of sleeping a fixed 600 ms. With a fixed sleep, a joining caller paused about 400 ms after the witness let the body finish inside its 200 ms bound (Codex round 3). A local probe pauses the caller a full second after the witness, and the fact still passes.

The test host is scheduled as on one core instead, and each run starts only once no CI job is on the desktop's runners.

- **StaThread.** `Run<T>` (`:108-160`) owns one `CancellationTokenSource timeout` per call, created on the *calling* thread before the STA thread starts; the STA delegate (`:117-128`) captures it and, first thing, stores its token in `[ThreadStatic] private static CancellationToken t_timeout` (the token, never the source — the slot is the STA thread's own). **New** `internal static CancellationToken Current => t_timeout` and `internal static bool TimedOut => t_timeout.IsCancellationRequested`. At `:139`, on the joining caller, `timeout.Cancel()` runs *before* `BeginInvokeShutdown`, so the STA body's token — the one it captured — is the one cancelled; the source is disposed after the final `Join`.
