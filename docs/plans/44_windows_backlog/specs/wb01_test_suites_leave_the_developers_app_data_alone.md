## Goal

A developer who runs `dotnet test` on either Windows project, or launches the app for an NVDA field pass, finds their own recent vaults, window placement, preferences, palette recents, per-vault file recents and sidebar write journal exactly as they left them. One device-state root, `SlateDeviceState.Root`, honours `SLATE_LOCAL_APP_DATA` the way `HostLog.LogDirectory` already honours `SLATE_LOG_DIR`; every store resolves through it; the test hosts and the shell gate point it at a per-run temporary root; a wrapper proves, after the whole run and its child processes have ended, that the real profile did not change; and a launch script seeds such a root for field passes (plan §4 rule 4). Production behaviour with the variable unset is byte-for-byte unchanged.

## Design

- **New** `apps/slate-windows/src/SlateWindows/SlateDeviceState.cs`, `internal static class SlateDeviceState`: `internal const string Variable = "SLATE_LOCAL_APP_DATA"`; `internal static string Resolve(string? overrideValue)` (pure: a non-empty value → `Path.GetFullPath(value)`, else `Path.Combine(LocalApplicationData, "Slate")`); `internal static string Root => Resolve(Environment.GetEnvironmentVariable(Variable))`, read at each use (cheap; a store captures its path at construction as today).
- The six stores compose from `SlateDeviceState.Root`: `recent-vaults.json`, `window-state.json`, `preferences.json`, `command-palette-recents.json` (the `{ get; }` at `CommandPaletteRecentsStore.cs:56` becomes `=>`), `file-recents\`, `sidebar-write-journal`. `FileRecentsStore` keeps its `localAppDataRoot` parameter (callers that pass one win). `HostLog.LogDirectory` becomes `SLATE_LOG_DIR ?? Path.Combine(SlateDeviceState.Root, "logs")`.
- **Test hosts.** `SlateWindows.Tests` gets a `[ModuleInitializer]` in **new** `tests/SlateWindows.Tests/Support/DeviceStateForTests.cs` that, unless `SLATE_LOCAL_APP_DATA` is already set, creates `%TEMP%\slate-tests-<pid>-<guid>` and sets the variable for the process (`DeviceStateForTests.Root`). The AccessibilityTests project gets the same in **new** `tests/SlateWindows.AccessibilityTests/ShellLaunch.cs`: **new** `internal static string ShellLaunch.Root` (`SLATE_LOCAL_APP_DATA` when already set, else a `%TEMP%\slate-gate-<pid>-<guid>` folder created on first use) and **new** `internal static void ShellLaunch.ApplyDeviceState(ProcessStartInfo startInfo)` (sets `startInfo.Environment["SLATE_LOCAL_APP_DATA"] = Root`), lazy so VSTest assembly mode (`windows.yml:845-848`, no project file) is covered without relying on a module initialiser; `StartShellProcess` (`:116-137`) and the 41 inline sites call it on their own `ProcessStartInfo` variable, whatever its name. Journeys that depend on recents (`Announcements.cs:57-66`, `ShellAccessibilityTests.cs:938`) keep passing — the per-run root starts empty, so a unique name reads bare, which is what they assert; their comments say the root is the run's own.
- **The whole-run guard is outside the process.** **New** `scripts/windows/guard-device-state.ps1`, invoked only as `pwsh -NoProfile -File guard-device-state.ps1 [-Profile <folder>] -- <command> [<argument>…]`. **It declares no `param` block and no `[CmdletBinding()]` or `[Parameter()]` attribute**, so it is not an advanced script and PowerShell's parameter binder never sees the command: it reads `$args` itself — an optional leading `-Profile <folder>` pair, then a required literal `--`, then at least one command token, every token passed to the command verbatim (`& $command[0] @rest`); any other shape writes `usage: pwsh -NoProfile -File guard-device-state.ps1 [-Profile <folder>] -- <command> [<argument>...]` to stderr and exits 2 before it snapshots or runs anything. Under `pwsh -File` the `--` reaches `$args`; an in-process `& guard-device-state.ps1 -- …` loses it to the parser and so fails as a usage error instead of misbinding. Without `-Profile` the profile is `Join-Path $env:LOCALAPPDATA 'Slate'` — the variable, which on Windows names the same folder as the known-folder API and which a test can point at a surrogate parent; an empty variable exits 2. The first output line is `guard-device-state: profile <folder>`. Why no declared parameters (reproduced in pwsh 7.6.7): `param([string]$Profile = …, [Parameter(ValueFromRemainingArguments)][string[]]$Command)` binds an in-process `-- dotnet test …` as `Profile='dotnet'`, `Command=@('test', …)`, and under `pwsh -File` fails on the `--` itself (`parameter name '' is ambiguous`), so neither CI call would inspect the intended profile or run the intended command; `[CmdletBinding(PositionalBinding = $false)]` with a positional remaining-arguments parameter still fails on `--` under `-File`, and without the `--` it binds dotnet's own `-c` to the wrapper's `-Command` and its `-v` to `-Verbose`. One `pwsh -File` limit the wrapper cannot undo: a `-name:value` token arrives split into `-name` and `value`; neither CI command nor the verification uses that form. Once parsed, it snapshots the profile recursively (relative path, length, last-write ticks; a folder that does not exist snapshots as empty, so creating it is a difference), records the ids of the `SlateWindows.exe` processes already running, runs the command (any `dotnet test …`, including the gate dll) and waits for it, then waits up to 60 s for every `SlateWindows.exe` that was not running before to exit (the shell gate's launches are grandchildren of `dotnet test` through the test host; a survivor past the bound could still write after the second snapshot, so it fails the run and is named by pid), snapshots again, prints every created, changed or removed file, and exits with the command's own exit code when that is nonzero (a failing test run stays failing under the wrapper), else 1 when the snapshots differ or a launch survived, else 0.
- **How each CI runner reaches the wrapper.** The unit lane has a checkout: its `Test` step (`windows.yml:527-534`) becomes `pwsh -NoProfile -File scripts/windows/guard-device-state.ps1 -- dotnet test …` with today's arguments unchanged. The gate runner has none (Current state), so the wrapper **travels in the artifact**: `SlateWindows.AccessibilityTests.csproj` gains, in the `:22-49` item group and with the same reason in its comment, `<Content Include="..\..\..\..\scripts\windows\guard-device-state.ps1" Link="tools\guard-device-state.ps1" CopyToOutputDirectory="PreserveNewest" />`; the upload's existing `apps/slate-windows/tests/SlateWindows.AccessibilityTests/bin/Release/**/*` path (`:559`) carries it with no upload change, and the download recreates it at `apps/slate-windows/tests/SlateWindows.AccessibilityTests/bin/Release/net10.0-windows/tools/guard-device-state.ps1`. The gate step (`:845-854`) becomes `pwsh -NoProfile -File apps/slate-windows/tests/SlateWindows.AccessibilityTests/bin/Release/net10.0-windows/tools/guard-device-state.ps1 -- dotnet test apps/slate-windows/tests/SlateWindows.AccessibilityTests/bin/Release/net10.0-windows/SlateWindows.AccessibilityTests.dll …` with its logger, results directory, blame options and `env:` unchanged, verbatim (so `W1ReleaseEvidenceContractTests.WindowsWorkflowRetainsAccessibilityEvidenceAfterGateFailure`, `W1HardeningTests.cs:81-95`, still finds them). The `flaui` job gains no checkout step. Both calls omit `-Profile` on purpose — they inspect the default, the runner's `%LOCALAPPDATA%\Slate` — and that exact shape (no `-Profile`, `--`, then the step's `dotnet test` arguments, including `--filter "FullyQualifiedName!~…"`, `--logger "trx;…"` and the `--blame-hang-*` pair) is the one `test_guard_device_state.py`'s default-profile tests run through `pwsh -NoProfile -File`; the step's own shell (pwsh, the Windows runner default) passes the `--` through to the `pwsh` it starts. So CI proves every run, not one fact. An in-process `DeviceStateGuardTests` fact still exists as the fast local signal, but the wrapper is the witness.
- The four bare constructions pass `localAppDataRoot: fixture-local path` (the `QuickSwitcherRankCoordinatorTests.cs:356` shape).
- **Pins rewritten:** `DefaultRecentsPath_IsTheGlobalDeviceLocalLocation` asserts `CommandPaletteRecentsStore.DefaultFilePath == Path.Combine(SlateDeviceState.Root, "command-palette-recents.json")` and gains a sibling, **new** `CommandRegistrationTests.DefaultRecentsPath_UnsetIsTheProfilesSlateFolder`, over `Resolve(null)` for the unset branch; `ATestProcessNeverJournalsIntoTheUsersAppData` asserts `ProductionDirectory` is under `SlateDeviceState.Root` and not under the real profile when the override is set.
- **Field-pass launcher**, **new** `scripts/windows/launch-for-field-pass.ps1`, declared `[CmdletBinding(PositionalBinding = $false)] param([string]$Vault, [switch]$Seed, [switch]$Keep, [string]$Exe, [string]$Root)` and always started as `pwsh -NoProfile -File scripts/windows/launch-for-field-pass.ps1 …`. **`-Vault` is one string, never an array:** one vault folder, or several joined by `|` (`-Vault "$a|$b"`), which the script splits itself. Why (reproduced in pwsh 7.6.7): `pwsh -File` cannot bind an array to a script parameter (about_pwsh: `-File` arguments arrive as literal strings). From PowerShell, `-Vault $a,$b` hands the child `pwsh` two separate tokens, so a `[string[]]$Vault` binds `$a` alone and the stray `$b` positionally to the next unbound parameter — `-Exe` (the launcher would start the second vault's folder as the program) or, when `-Exe` is given, `-Root` (it would adopt the second vault as the device-state root and seed `recent-vaults.json` into it); a literal `a,b` arrives as the one string `a,b`; and a repeated `-Vault` is a binder error. `|` is the separator because no Windows path can hold it (a reserved Win32 file-name character, and in `[IO.Path]::GetInvalidPathChars()`), while `;`, the `PATH` separator, is a legal file-name character. `PositionalBinding = $false` turns the old spelling into a binder error before the body runs (nonzero exit, `A positional parameter cannot be found that accepts argument …`); in process, `-Vault $a,$b` is refused too (`Cannot convert value to type System.String`). **Parsing, before a root is created or anything starts:** split on `|`, trim each entry, keep the order; exit 2 with a `launch-for-field-pass: <reason>` line on stderr when the list or any entry is empty or whitespace (`-Vault ''`; a leading, trailing or doubled `|`), an entry is not fully qualified (`[IO.Path]::IsPathFullyQualified`), an entry is not an existing folder (`Test-Path -LiteralPath … -PathType Container`), two entries name one folder (`[IO.Path]::GetFullPath`, ending separator trimmed, compared `OrdinalIgnoreCase` as `RecentVaultsStore.Add` does, `RecentVaultsStore.cs:140-141`), the list holds more than eight (`RecentVaultsStore.MaxEntries`, `:54`, past which `Load` truncates silently), or `-Seed` comes without `-Vault`. Without `-Vault` the app starts with no argument. Without `-Root` the launcher creates `$env:TEMP\slate-field-pass-<yyyyMMdd-HHmmss>`; with `-Root` it reuses that existing folder (it must exist and hold no file outside `recent-vaults.json`, the other device stores and `logs\`, else exit 2) so a pass that relaunches reads the same device state. It sets `$env:SLATE_LOCAL_APP_DATA` to the root and `$env:SLATE_LOG_DIR` beneath it; with `-Seed` it writes `recent-vaults.json` — UTF-8 without a BOM, `ConvertTo-Json -InputObject @(…)` so one vault is still a JSON array (piping a one-element array to `ConvertTo-Json` writes a bare object, which `RecentVaultsStore.Load` reads as no recents) — with one record per entry in list order, the shape `RecentVault.FromPath` makes (`RecentVaultsStore.cs:16-30`: `path` = `[IO.Path]::GetFullPath(entry)`, `displayName` its last segment, `lastOpenedMs` strictly decreasing, so the first is the most recent and a pass can seed two vaults whose names collide). It prints `Root: <path>`, then starts `$Exe` (default `apps/slate-windows/src/SlateWindows/bin/Release/net10.0-windows/SlateWindows.exe`, the layout `windows.yml:848` uses for the gate dll) through a `[System.Diagnostics.ProcessStartInfo]` with `UseShellExecute = $false` and the first vault as its only `ArgumentList` entry (a path with spaces arrives as one argument; `Start-Process -ArgumentList` would split it), waits for that process to exit, and then deletes the root unless `-Keep` or `-Root` was given (a reused root is never deleted). Every field pass in plan 44 launches through it (§4 rule 4); environment variables set in the calling window (a `SLATE_TEST_*` diagnostic seam) reach the app because the launcher and the app are child processes that inherit them.
- Deliberately not changed: `ReadingSurface.cs:739`, the stores' file formats and names, `InstallProductionLocation`'s call site, production defaults when the variable is unset.
