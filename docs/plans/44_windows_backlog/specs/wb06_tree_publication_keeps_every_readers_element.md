# WB-6 — Tree publication keeps every reader's element: date groups, organic publications, and the vanished selected row

Issues: #1522 #1515 (both close here). Size M. Lanes: windows + FlaUI. AT: NVDA spot. Wave: W2 (slot 3). Depends on: nothing (20b and #1523 are on `main`). Parallel with: WB-4, WB-5. Decision: WD3 (pending; recommended "yes, cases 1 and 3 ship now with #1522"; under the other answer: #1522 alone ships, the organic replace and the selected-row fallback stay, the PR writes `Refs #1515` and the issue stays open with a comment naming the two cases).

## Goal

Since 20b (#1507) and #1523, a rescan's publication of the Files tree keeps every row it did not change, so a screen reader or a scan holding a row's UI Automation element still holds a live row. Three holes remain, and this chunk closes them: with Group by date on, every date group and every row under it is replaced on every run (#1522); an organic publication (after Slate's own create, rename, duplicate, move, delete or a settings change) still replaces the whole tree (#1515 case 1); and when the publication removes the selected row the whole tree is replaced because WPF's `TreeView.OnItemsChanged` would otherwise select the first row, which opens its note (#1515 case 3). After this chunk the rule is total: a reader's row never gets a new element for a change elsewhere, and a vanished selected row lands the keys on the nearest survivor focused without selection, with no note opened and no selection announced.

## Design

**Date groups (#1522).** A group header becomes a keyed row: `IsKeyedRow` admits `IsGroupHeader` rows, and `PlanLevel` keys them by `(parent, label)`: the dictionary key for a group is `"\u0000group:" + Name` (a file path never contains NUL, so it cannot collide with a file key) within the level being planned, which already is one parent. `IsTheSameRow` compares expansion only for non-group rows (a fresh group is always built expanded, `:55`), so the published group's `IsExpanded` is the truth and `ReconcileLevel`'s `TakeRowStateOf` (`:304`) must not copy it for a group (verify the method; add the guard). A kept group recurses like a kept open folder: `ListsItsRowsAgain` admits a group whose `IsExpanded` is true, and `PlanLevel` plans its children against the fresh group's. A file whose bucket changed is not planned under its old group (its fresh row is under another group), so `ReconcileLevel` releases it from the old group and attaches the fresh row to the new one: a removal and an insertion. `GroupFilesByDate` is unchanged. A collapsed group's rows are not planned (`ListsItsRowsAgain` requires `IsExpanded`), so they are adopted through `AdoptChildStateOf` as a collapsed folder's are (`:358`).

**Organic publications (#1515 case 1).** `ApplyTreeRefresh` takes the keep path for every publication: the `silent` branch at `TreeOperations.cs:608-614` collapses to `PublishKeepingUnchangedRows(outcome.RootNodes)`. The pending restores (`ConsumePendingRenameArm`, `ConsumePendingSelection`, `ConsumePendingSurfaceSelection`) look nodes up by path in `RootNodes` after the publication; they find kept nodes or fresh ones alike (read `FileManagement.cs:610-627` and the rename-arm consumer before coding: if either holds a node reference captured before the publication, resolve it by path). `ApplyTags(outcome.Tags, announce: !silent)` keeps its `silent` flag; nothing else in the method reads it.

**The selected row removed (#1515 case 3).** `PublishKeepingUnchangedRows` drops the second half of its fallback (`SelectedNode` not kept) and keeps only `kept.Count == 0`. Before `ReconcileLevel` mutates any collection, when `SelectedNode is { } selected && !kept.ContainsKey(selected)`: a new `DeselectBeforeRemoval(selected)` clears **both halves** of the selection — `selected.IsSelected = false` first (the two-way binding at `MainWindow.xaml:1167` clears the container's `TreeViewItem.IsSelected`, so WPF's `TreeView` has no selected container to replace when the row leaves), then `SetField(ref _selectedNode, null, nameof(SelectedNode))` (the property name named explicitly, as `SelectSilently` does) and `RaiseCommandStates()`. Then `ReconcileLevel` runs; the removed container unloads with nothing selected, so `base.OnItemsChanged` selects no first row. After the reconcile, a shared helper `RecordVanishedSelection(previousRoots, selected)` (extracted from `ReconcileSelectionAfterPublication :666-673`) computes `NearestSurvivor` over the published tree, sets `_vanishedSelection = new VanishedSelection(survivor)` and raises `TreeSelectionRestored` once; `ReconcileSelectionAfterPublication` itself returns early because `SelectedNode` is already null (`:648-651`). The window's restore (`MainWindow.ShellRegions.cs:1077-1083` `KeysStrandedFromFilesTree`) lands the keys on the survivor through `SelectorFocus.FocusRowUnselected` (`:1060`) — R-5's focus-without-select. If the lane shows the recycled container still holds the keys with a live `PresentationSource` (so `KeysStrandedFromFilesTree` is false), `KeysOnARemovedFilesRow` gains the issue's second clause: `ItemsControl.ItemsControlFromItemContainer(row)?.ItemContainerGenerator.ItemFromContainer(row) == DependencyProperty.UnsetValue`. A hosted fact asserts all of: `TreeView.SelectedItem` null, no container with `IsSelected` true, `SelectedNode` null, no tab opened, no selection or open announcement.

**Not changed:** `GroupFilesByDate`, `DateBucket`, `RealizedRowHold`, `NearestSurvivor`'s order, `IsTheSameRow`'s other clauses, `LandingTreeView.OnItemsChanged`, the tag tree, the filter.
