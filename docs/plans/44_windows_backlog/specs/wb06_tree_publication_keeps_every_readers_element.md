## Goal

Since 20b (#1507) and #1523, a rescan's publication of the Files tree keeps every row it did not change, so a screen reader or a scan holding a row's UI Automation element still holds a live row. Three holes remain, and this chunk closes them: with Group by date on, every date group and every row under it is replaced on every run (#1522); an organic publication (after Slate's own create, rename, duplicate, move, delete or a settings change) still replaces the whole tree (#1515 case 1); and when the publication removes the selected row the whole tree is replaced because WPF's `TreeView.OnItemsChanged` would otherwise select the first row, which opens its note (#1515 case 3). After this chunk the rule is total: a reader's row never gets a new element for a change elsewhere, and a vanished selected row lands the keys on the nearest survivor focused without selection, with no note opened and no selection announced, while a selected note the publication only rebuilt (it changed date group, or the grouping changed) stays selected on its new row.

## Design

**Date groups (#1522).** A group header becomes a keyed row: `IsKeyedRow` admits `IsGroupHeader` rows, and `PlanLevel` keys them by `(parent, label)`: the dictionary key for a group is `"\u0000group:" + Name` (a file path never contains NUL, so it cannot collide with a file key) within the level being planned, which already is one parent. `IsTheSameRow` compares expansion only for non-group rows (a fresh group is always built expanded, `:55`), so the published group's `IsExpanded` is the truth and `ReconcileLevel`'s `TakeRowStateOf` (`:304`) must not copy it for a group (verify the method; add the guard). A kept group recurses like a kept open folder: `ListsItsRowsAgain` admits a group whose `IsExpanded` is true, `ReconcileLevel`'s skip of every non-folder row (`if (!row.IsDirectory) continue;`, `RescanReconcile.cs:178-181`) admits group headers too, and `PlanLevel` plans its children against the fresh group's. A file whose bucket changed is not planned under its old group (its fresh row is under another group), so `ReconcileLevel` releases it from the old group and attaches the fresh row to the new one: a removal and an insertion. `GroupFilesByDate` is unchanged. A collapsed group's rows are not planned (`ListsItsRowsAgain` requires `IsExpanded`), so they are adopted through `AdoptChildStateOf` as a collapsed folder's are (`:358`).

**Organic publications (#1515 case 1).** `ApplyTreeRefresh` takes the keep path for every publication: the `silent` branch at `TreeOperations.cs:608-614` collapses to `PublishKeepingUnchangedRows(outcome.RootNodes)`. The pending restores (`ConsumePendingRenameArm`, `ConsumePendingSelection`, `ConsumePendingSurfaceSelection`) look nodes up by path in `RootNodes` after the publication; they find kept nodes or fresh ones alike (read `FileManagement.cs:610-627` and the rename-arm consumer before coding: if either holds a node reference captured before the publication, resolve it by path). `ApplyTags(outcome.Tags, announce: !silent)` keeps its `silent` flag; nothing else in the method reads it.

**The selected row not kept (#1515 case 3).** `PublishKeepingUnchangedRows` drops the second half of its fallback (`SelectedNode` not kept) and keeps only `kept.Count == 0`; it takes no selection parameter. Before `ReconcileLevel` mutates any collection, when `SelectedNode is { } selected && !kept.ContainsKey(selected)`: `ReaderRows()` is read first (so the folders the row was in still anchor their levels in `RowsThatStay`), then a new `private void DeselectBeforeRemoval(FileTreeNodeViewModel selected)` disarms **both halves** of the selection — `selected.IsSelected = false` first (the two-way binding at `MainWindow.xaml:1167` clears the container's `TreeViewItem.IsSelected`, so WPF's `TreeView` has no selected container to replace when the row leaves), then `SetField(ref _selectedNode, null, nameof(SelectedNode))` (the property name named explicitly, as `SelectSilently` does) and `RaiseCommandStates()`. Then `ReconcileLevel` runs; the outgoing container unloads with nothing selected, so `base.OnItemsChanged` selects no first row. `PublishKeepingUnchangedRows` resolves nothing more: a row the reconcile did not keep is not always a row that is gone (next paragraph), and a mutation's named successor must win. The resolution stays `ReconcileSelectionAfterPublication`'s, the last selection step of `ApplyTreeRefresh` on both paths, after `ConsumePendingRenameArm`, `ConsumePendingSelection` and `ConsumePendingSurfaceSelection` (`TreeOperations.cs:623-631`). That order is main's: Slate's rename or move of the selected row names its new path (`RequestSelectionAt(newPath)`, `FileManagement.cs:264`, `:962`), the pending selection seats it, and the reconcile then finds a selected row in the tree and does nothing. Resolving the unkept row inside `PublishKeepingUnchangedRows`, before the pending consumers, would land the keys on the old row's neighbour and then on the renamed row — two focus changes where R-9 (a) allows one.

**A selected row not kept, but still there.** The reconcile keeps a row only when `PlanLevel` matched it at its own level under a kept parent, so the selected node can be released while a row with its path is published: (1) its date bucket changed — the note left one group for another (the first rescan after midnight moves every "Today" note to "Yesterday"); (2) the grouping changed under it — `GroupByDate` turned on or off, or a Created ↔ Modified sort under grouping; both setters call the organic `Refresh()` (`FilesSidebarViewModel.cs:685-707`, `:709-731`), which now takes the keep path, and the note moves between the root and a group; (3) a parent the reconcile did not keep — `PlanLevel` recurses only through kept rows (`RescanReconcile.cs:111-123`), so every row under an unkept open folder is a fresh node even where its path survived; (4) a selected date group header under such a parent: every group's and every placeholder's `Path` is `""` (`FilesSidebarViewModel.cs:46`, `:54`), so main's same-path match (`Flatten(RootNodes).FirstOrDefault(node => node.Path == current.Path)`, `FileManagement.cs:658-663`) takes the first empty-path row, any group or a placeholder. Main recovers (1)–(3) by path on its replace path (`:658-663`); resolving them as vanished would clear the selection and move the keys off a note that still exists. So `ReconcileSelectionAfterPublication(SelectionPlace? place)` resolves in this order, on both paths:
- `place` is null (nothing was selected before the publication), or `SelectedNode` is in the published tree (kept, or a pending restore seated it): nothing to do.
- Else the **same-key replacement**: the published row, anywhere in the tree, whose `RowKey` (below) is `place.SelectedKey` — for a file or folder its path, for a group header its parent's path and its label, so (4) finds its own group. It is re-seated through `SelectSilently(replacement, reseatOf: place.SelectedPath)`. Its landing is the replacement itself when the published tree shows it (every ancestor expanded), else new `private static FileTreeNodeViewModel ShownRowHolding(FileTreeNodeViewModel row, IEnumerable<FileTreeNodeViewModel> roots)` — the outermost collapsed row above it, the row the reader sees: a note that moved into a date group the reader collapsed lands the keys on that group's header, the group stays collapsed, and the row shows selected when the group is opened.
- Else the row is gone: `SelectedNode` is cleared if it is still set (the replace path's stale node) and the landing is `NearestSurvivor(place)` (null: the tree's own landing).

Then new `private void RecordSelectionLanding(FileTreeNodeViewModel? landing)` (extracted from `ReconcileSelectionAfterPublication :666-673`) sets `_vanishedSelection = new VanishedSelection(landing)` and raises `TreeSelectionRestored` once; the window's restore (`MainWindow.xaml.cs:427-447`) lands the keys there through `LandNearVanishedSelection` and `SelectorFocus.FocusRowUnselected` (`MainWindow.ShellRegions.cs:1055-1060`) — a re-seated replacement is already selected, so focusing it selects nothing new; a survivor or a collapsed group header is focused without selection (R-5's focus-without-select). On the replace path this adds the landing record to main's same-path re-seat, which raised nothing. `SelectSilently` gains a parameter, new signature `private void SelectSilently(FileTreeNodeViewModel node, string? reseatOf = null)`: the name field is kept when `reseatOf ?? previous?.Path` equals `node.Path` (main compares `previous?.Path` only, `FilesSidebarViewModel.cs:795`, and after the disarm `previous` is null), so a re-seat keeps a mid-typed inline rename as main's same-path re-seat does (#1136); every other caller passes nothing and is unchanged. If the lane shows the recycled container still holds the keys with a live `PresentationSource` (so `KeysOnARemovedFilesRow` is false and the window's synchronous landing does not run), `KeysOnARemovedFilesRow` gains the issue's second clause: `ItemsControl.ItemsControlFromItemContainer(row)?.ItemContainerGenerator.ItemFromContainer(row) == DependencyProperty.UnsetValue`. A hosted fact asserts, for a row that is gone, all of: `TreeView.SelectedItem` null, no container with `IsSelected` true, `SelectedNode` null, no tab opened, no selection or open announcement; for a re-seated row: `SelectedNode` the replacement, its container selected and holding the keys, the name field unchanged, nothing opened or announced.

**The vanished row's place is read before anything moves.** On the keep path `NearestSurvivor` can no longer walk the old tree after the publication: `previousRoots` copies the root collection only (`TreeOperations.cs:606`) and `ReconcileLevel` has removed the selected row from its kept folder's or kept group's own `Children` (`RescanReconcile.cs:190-204`), so `FindSiblings` finds nothing (`FileManagement.cs:716-720`) and deleting a selected `folder/b.md` would land the keys on the tree's first row instead of `folder/c.md` or `folder`. So the place is snapshotted first and resolved last:
- New `private sealed record SelectionPlace(string SelectedKey, string SelectedPath, IReadOnlyList<string> CandidateKeys)` and new `private SelectionPlace? SnapshotSelectionPlace()`, called at the top of `ApplyTreeRefresh` in place of the `previousRoots` copy (`TreeOperations.cs:606`) — before `PublishKeepingUnchangedRows`, so before `DeselectBeforeRemoval` clears `SelectedNode` and before `ReconcileLevel` mutates any collection, and before the replace path too. Null when nothing is selected. Otherwise it records the selected row's own `RowKey` (`SelectedKey`) and `Path` (`SelectedPath`), and walks the published, still untouched tree once to record, in `NearestSurvivor`'s order (its loop `FileManagement.cs:712-737`, unrolled while the tree has not moved), the keys of: the selected row's next siblings in order, then its previous siblings nearest first, then its parent; then the parent's next siblings, its previous siblings, the grandparent; and so on up to the root level.
- New `private static string? RowKey(FileTreeNodeViewModel row, string parentPath)`: a file's or folder's `Path`; for a date group header `parentPath + "\u0000group:" + Name` — the key `PlanLevel` gives a group within its level, prefixed with the path of the folder the group is in (`""` at the root) so it is unique across the tree (a file path never holds NUL); null for a placeholder (never a candidate, never a replacement).
- `NearestSurvivor` becomes `private FileTreeNodeViewModel? NearestSurvivor(SelectionPlace place)`: it keys the published tree's shown rows (`ShownRows`, `:741-754`: every ancestor expanded) by `RowKey`, tracking each row's parent folder path as it descends, and returns the first candidate key found, or null (the tree's own landing). The order is unchanged; what changes is that the candidates come from the snapshot and that a surviving date group header can take the keys — it is a selectable row (`FilesSidebarViewModel.cs:607`), and under Group by date a row's parent is its group, which R-9 (a)'s "else its parent" names; today's path-only lookup skips headers (`:708`).
- `ReconcileSelectionAfterPublication(SelectionPlace? place)` (its parameter was `previousRoots`) is the one resolver, on the keep path and on the replace path (`kept.Count == 0`) alike, so one model serves both paths and nothing reads the old tree after the publication; `PublishKeepingUnchangedRows(fresh)` only disarms.

**Not changed:** `GroupFilesByDate`, `DateBucket`, `RealizedRowHold`, `NearestSurvivor`'s order (its candidates' source and resolution change, above), `IsTheSameRow`'s other clauses, `LandingTreeView.OnItemsChanged`, the tag tree, the filter.
