# WB-6 — Tree publication keeps every reader's element: date groups, organic publications, and the vanished selected row

Issues: #1522 #1515 (both close here). Size M. Lanes: windows + FlaUI. AT: NVDA spot. Wave: W2 (slot 3). Depends on: nothing (20b and #1523 are on `main`). Parallel with: WB-4, WB-5. Decision: WD3 (pending; recommended "yes, both cases now").

## Goal

Since 20b (#1507) and #1523, a rescan's publication of the Files tree keeps every row it did not change, so a screen reader or a scan holding a row's UI Automation element still holds a live row. Three holes remain, and this chunk closes them: with Group by date on, every date group and every row under it is replaced on every run (#1522); an organic publication (after Slate's own create, rename, duplicate, move, delete or a settings change) still replaces the whole tree (#1515 case 1); and when the publication removes the selected row the whole tree is replaced because WPF's `TreeView.OnItemsChanged` would otherwise select the first row, which opens its note (#1515 case 3). After this chunk the rule is total: a reader's row never gets a new element for a change elsewhere, and a vanished selected row lands the keys on the nearest survivor focused without selection, with no note opened and no selection announced.

## Design

**Date groups (#1522).** A group header becomes a keyed row: `IsKeyedRow` admits `IsGroupHeader` rows, and `PlanLevel` keys them by `(parent, label)`: the dictionary key for a group is `"\u0000group:" + Name` (a file path never contains NUL, so it cannot collide with a file key) within the level being planned, which already is one parent. `IsTheSameRow` already compares `Name`, `IsDirectory` (false for both), `Level` and `IsExpanded`; for a group `candidate.IsExpanded` is always true, so the comparison takes the published row's expansion as the truth: `IsTheSameRow` compares expansion only for non-group rows, and `ReconcileLevel`'s `TakeRowStateOf` does not touch `IsExpanded` (verify; `:304`). A kept group recurses like a kept open folder: `ListsItsRowsAgain` admits a group (`IsGroupHeader`, its children already loaded), and `PlanLevel` plans its children against the fresh group's. A file whose bucket changed is not planned under its old group (its fresh row is under another group), so `ReconcileLevel` releases it from the old group and attaches the fresh row to the new one: a removal and an insertion, as the issue asks. `GroupFilesByDate` is unchanged; the fresh groups still come expanded, and the reconcile keeps the published one's `IsExpanded`. A collapsed group's rows are not planned (`ListsItsRowsAgain` requires `IsExpanded`), so they are adopted through `AdoptChildStateOf` as a collapsed folder's are (`:358`).

**Organic publications (#1515 case 1).** `ApplyTreeRefresh` takes the keep path for every publication: the `silent` branch at `TreeOperations.cs:608-614` collapses to `PublishKeepingUnchangedRows(outcome.RootNodes)`. The pending restores (`ConsumePendingRenameArm`, `ConsumePendingSelection`, `ConsumePendingSurfaceSelection`) look nodes up by path in `RootNodes` after the publication; they find kept nodes or fresh ones alike (read `FileManagement.cs:610-627` and the rename-arm consumer before coding: if either holds a node reference captured before the publication, resolve it by path). `ApplyTags(outcome.Tags, announce: !silent)` keeps its `silent` flag; nothing else in the method reads it.

**The selected row removed (#1515 case 3).** `PublishKeepingUnchangedRows` drops the second half of its fallback (`SelectedNode` not kept) and keeps only `kept.Count == 0`. Before `ReconcileLevel` runs, when `SelectedNode` is not in `kept`: compute `survivor = NearestSurvivor(previousRoots, selected)` over the fresh tree's shown rows (the method reads `RootNodes` — call it after the reconcile instead, with the kept rows in place, which is what `ReconcileSelectionAfterPublication(previousRoots)` already does at `:666`), and disarm the selection *before* the row leaves the collection: `SetField(ref _selectedNode, null)` plus `RaiseCommandStates()`, so that when `ReconcileLevel` removes the container WPF's `TreeView.OnItemsChanged` finds no selected container to replace. Then `ReconcileSelectionAfterPublication` runs as today: `SelectedNode` is null, so it returns early (`:648-651`); move the vanished-selection recording into a shared helper (`DisarmVanishedSelection(previousRoots, current)`) that both paths call so `_vanishedSelection = new VanishedSelection(survivor)` and `TreeSelectionRestored` fire once. The window's restore (`MainWindow.ShellRegions.cs`, `KeysStrandedFromFilesTree :1077-1083`) lands the keys on the survivor through `SelectorFocus.FocusRowUnselected` (`:1060`) — R-5's focus-without-select — because the keys are stranded on a row whose container has unloaded; if the lane shows the recycled container still holds the keys with a live `PresentationSource`, `KeysOnARemovedFilesRow` gains the issue's second clause ("a focused container its items control no longer maps to an item": `ItemsControl.ItemsControlFromItemContainer(row)?.ItemContainerGenerator.ItemFromContainer(row) == DependencyProperty.UnsetValue`). WPF's automatic first-row selection is suppressed by the disarm, not by overriding `OnItemsChanged` — a hosted fact proves no `SelectedNode` is set, no note opens and no selection announcement is posted.

**Not changed:** `GroupFilesByDate`, `DateBucket`, `RealizedRowHold`, `NearestSurvivor`'s order, `IsTheSameRow`'s other clauses, the tag tree, the filter.
