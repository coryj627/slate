# WB-9 — Open, handoff and landing lifecycle: a handoff parks behind a modal, the welcome view holds the keys through the scan, and a rescan reload carries a held reading landing

Issues: #1296 #1319 #1312 (all close here). Size M. Lanes: windows. AT: NVDA (full pass). Wave: W3 (slot 3). Depends on: nothing. Parallel with: WB-7, WB-8 (WB-8 touches `EditorInteractions.cs`, not these files). Decision: WD4 (pending; recommended "the welcome view stays, with a live Opening vault… status").

## Goal

Three lifecycle holes a screen-reader user hears as a dead key, a stray focus change or a vault switching under a dialog. After this chunk: a second launch or jump-list open that arrives while a modal loop runs over the shell (or a palette command is sealed) is parked and runs once when the loop ends, the last request winning (#1296); an ordinary two-turn vault open moves the keys exactly once, from the welcome view to the launch landing, never to the bare window, and a failed open leaves them on the welcome view (#1319, R-5 (h)); and a reading-mode tab's held F6 landing survives a rescan's in-place reload of that same tab, seating and speaking once on the reloaded projection, while every other rebind still withdraws it (#1312, R-9/R-10).

## Design

**#1296 — the handoff parks.** `MainWindow` gains `string? _parkedExternalActivation` and `bool _externalActivationParked`. `ActivateFromExternalRequestAsync` keeps its show/restore/activate lines (the window may come forward; the dialog keeps focus because it is owned by the window), then: if `_modalLoops.IsModalLoopActive || _viewModel.Palette.IsSealed`, record the request (`_parkedExternalActivation = vaultPath; _externalActivationParked = true;` — the last received wins, a null path parks too so a bare activation still brings the window forward when the loop ends) and return. `ModalLoopChanged(false)` (`MainWindow.ShellRegions.cs:244`) and the palette's unseal (new `CommandPaletteViewModel.SealReleased` event, raised in the `finally` at `:865` when `!IsSealed` after `_isInvoking = false`, and in `SetModalLoop(false)` when the seal lifts) both call a new `RunParkedExternalActivation()`: takes the parked request, clears both fields, and if the shell is still sealed or modal (a second loop opened inside the first's end) parks it again; otherwise `_ = ActivateFromExternalRequestAsync(path)` on the dispatcher at `Input` priority (after the loop's own teardown). The `IsBusy` early return in `OpenVaultAsync` is unchanged (a handoff during an open is still refused silently today — out of scope, the issue does not name it). Not changed: `App.QueueActivation`, the pipe, the palette's own seal mechanics.

**#1319 — the welcome view holds the keys (WD4).** `VaultLifecycleViewModel` gains `public bool IsOpening` (true from `:515` until `InitializeWorkspace` returns or the open fails) and `OpeningStatusText` (`"Opening vault…"`, then `ScanProgress.Started`'s "Scanning N files…" through `StatusText`'s existing updates — the welcome shows `StatusText` itself). `IsVaultOpen = true` moves from `:515` to the success branch at `:547`, immediately before `InitializeWorkspace` (same dispatcher turn, so the one-turn shape the existing fact pins is now the only shape). `VaultOpened`'s announcement, `AddRecentVault`, `VaultPath`, `VaultDisplayName` stay at `:516-519` (the four launch lines are untouched: `VaultOpened`, `VaultScanStarted`/`VaultScanFinished`, F1's lines; `IsVaultOpen`'s move changes no announcement). The welcome view (`MainWindow.xaml:775`) gains, under the subtitle, a `TextBlock` bound to `StatusText`, visible while `IsOpening`, with `AutomationProperties.LiveSetting="Polite"` — the live status WD4 names; NVDA's pass confirms it reads once and does not displace the launch lines. The Open button and the recents' buttons stay enabled during the open so nothing disables under the keys: `_openVaultCommand`'s predicate becomes `() => !IsBusy || IsOpening` (the recents command likewise, `:247`), and `OpenVaultAsync`'s `IsBusy` return (`:438-441`) re-reports the opening status instead of returning silently, so a press during the open is not a dead key. A failed open: `IsOpening = false`, `ReportTerminalStatus` as today, `ReturnedToWelcome` still focuses `OpenVaultButton` (now a no-op move when the keys never left it; the fact asserts zero focus changes). The welcome's `RegionFocusGuard` landing (R-5 (h) lists the welcome view) needs no change. If the owner answers WD4 otherwise (attach the shell before the scan): `IsVaultOpen` stays where it is, `InitializeWorkspace` splits into attach-then-populate, the launch landing lands the Files region before the scan and the scan's lines follow — a larger change this spec does not detail.

**#1312 — the carried landing.** The tab marks the swap: `WorkspaceTabViewModel` exposes `internal bool ReplacingReadingForRescan => _reloadingForRescan` (field `WorkspaceViewModel.cs:1820`). `ReadingSurface.OnModelChanged` (`:233-239`): before `WithdrawFocusLanding()`, if `surface._model is { } previous && previous.Tab is { ReplacingReadingForRescan: true } && ReferenceEquals(previous.Tab, incoming.Tab)` (both models belong to the same tab; `ReadingContentViewModel` holds its tab — verify the field name, it is the `this` passed at `WorkspaceViewModel.cs:581`) and `_focusLandingPending`, capture `(announce, refuse, park)` into a `_carriedLanding` tuple, withdraw, bind the new model, then re-request: `RequestFocusLanding(announce, refuse, park)` against the incoming model. The re-request's token is the incoming model's generation, so a later apply seats it once and `DeliverFocusLanding` speaks its one pane line; a failed reload (`Model_TornDown` before any apply, or `LastRefreshFailed`) refuses it silently through the existing refusal path (`fellThrough` callback: the F6 ring moves on, as `ARefusedEditorLandingResumesThePressPastIt` already pins for canvas). The window's slot: the `HeldEditorLanding`'s `isLive`/`stillWhereAsked` closures read the surface's pending state and the tab, so the carry keeps the slot's hold (same tab, same group); a tab or group change, a deactivation and an opening modal still withdraw through `ScopeChanged`, `WindowDeactivated`, `ModalOpened` unchanged. Not changed: `ReplaceItemWithReadText`, `ReloadKeepingCaretLine`, the re-seat path's caret rule, canvas re-seats.
