# WB-9 — Open, handoff and landing lifecycle: a handoff parks behind a modal, the welcome view holds the keys through the open, and a rescan reload carries a held reading landing

Issues: #1296 #1319 #1312 (all close here). Size M. Lanes: windows. AT: NVDA (full pass). Wave: W3 (slot 3). Depends on: nothing. Parallel with: WB-7, WB-8 (WB-8 touches `EditorInteractions.cs`, not these files). Decision: WD4 (pending; recommended "the welcome view stays, with a live Opening vault… status, until `WorkspaceReady`"; under the other answer — attach the shell before the scan — `IsVaultOpen` stays where it is, `InitializeWorkspace` splits into attach-then-populate and the launch landing lands the Files region before the scan; that variant is not detailed here).

## Goal

Three lifecycle holes a screen-reader user hears as a dead key, a stray focus change or a vault switching under a dialog. After this chunk: a second launch or jump-list open that arrives while a modal loop runs over the shell (or a palette command is sealed) is parked and runs once when the loop ends, the last request winning (#1296); an ordinary vault open — every asynchronous phase of it, from the session open to the scan — moves the keys exactly once, from the welcome view to the launch landing, never to the bare window, and a failed open leaves them on the welcome view (#1319, R-5 (h)); and a reading-mode tab's held F6 landing survives a rescan's in-place reload of that same tab, seating and speaking once on the reloaded projection, while every other rebind still withdraws it (#1312, R-9/R-10).

## Design

**#1296 — the handoff parks.** `MainWindow` gains `string? _parkedExternalActivation` and `bool _externalActivationParked`. `ActivateFromExternalRequestAsync` keeps its show/restore/activate lines (the window may come forward; the dialog keeps focus because it is owned by the window), then: if `_modalLoops.IsModalLoopActive || _viewModel.Palette.IsSealed`, record the request (`_parkedExternalActivation = vaultPath; _externalActivationParked = true;` — the last received wins; a null path parks too so a bare activation still brings the window forward when the loop ends) and return. `ModalLoopChanged(false)` (`MainWindow.ShellRegions.cs:244`) and a new `CommandPaletteViewModel.SealReleased` event (raised in the `finally` at `:865` when `!IsSealed` after `_isInvoking = false`, and in `SetModalLoop(false)` when the seal lifts) both call a new `RunParkedExternalActivation()`: takes the parked request, clears both fields, and if the shell is still sealed or modal (a second loop opened inside the first's end) parks it again; otherwise `_ = ActivateFromExternalRequestAsync(path)` on the dispatcher at `Input` priority (after the loop's own teardown). The `IsBusy` early return in `OpenVaultAsync` is unchanged (a handoff during an open is refused silently today — out of scope, the issue does not name it). Not changed: `App.QueueActivation`, the pipe, the palette's own seal mechanics.

**#1319 — the welcome view holds the keys through every phase (WD4).** `VaultLifecycleViewModel` gains `public bool IsOpening` (notifying), set to true **at admission, before `IsBusy = true` at `:475` and before the first await at `:483`**, and cleared on every exit of `OpenVaultAsync` — the stale-generation returns (`:484-488`), the success branch after `InitializeWorkspace`, both catch arms, and the `finally` at `:585-592` (a single `finally` that clears it when `generation == _generation`). `IsVaultOpen = true` moves from `:515` to the success branch at `:547`, immediately before `InitializeWorkspace` (same dispatcher turn, so the one-turn shape the existing fact pins is now the only shape). `VaultOpened`'s announcement, `AddRecentVault`, `VaultPath`, `VaultDisplayName` stay at `:516-519` (the four launch lines are untouched). The welcome view (`MainWindow.xaml:775`) gains, under the subtitle, a `TextBlock` bound to the existing `StatusText` (no new property: `StatusText` is already "Opening {root}…" from `:478` and the scan's progress lines after), visible while `IsOpening`, with `AutomationProperties.LiveSetting="Polite"` — the live status WD4 names; NVDA's pass confirms it reads once and does not displace the launch lines. Nothing disables under the keys: `_openVaultCommand`'s predicate becomes `() => !IsBusy || IsOpening` and the recents command's likewise (`:245-247`), and `OpenVaultAsync`'s `IsBusy` return (`:438-441`) re-reports `StatusText` through `ReportStatus` instead of returning silently, so a press during the open is not a dead key. A failed open: `IsOpening = false`, `ReportTerminalStatus` as today, `ReturnedToWelcome` still focuses `OpenVaultButton` (a no-op move when the keys never left it; the fact asserts zero focus changes). New ctor seam `Func<string, Task<VaultSession>>? openSession` (default `root => Task.Run(() => VaultSession.OpenFilesystem(root))`) beside `sessionLoadWorker`, so a fact can park the `OpenFilesystem` phase itself.
