## Goal

Four small truths. A folder's own "modified" notification (NTFS updates a folder's entry lazily when a handle closes) starts a silent Watcher rescan although nothing the scanner reads changed; core drops it (#1516). A Bases export saved inside the open vault is the one host-side write into the vault, so the watcher's run speaks "Files refreshed. 1 new or changed, 0 removed." a second after "Exported."; written through core it is an echo and one sentence (#1508). `GraphConfigStore.Write` recreates a renamed vault's old root; through `AnchoredVaultStore` it refuses and logs (#1475 bullet 1). A pin whose note is gone stays in `sidebar.json` forever on Windows; mac prunes lazily on a level fetch, and Windows now does the same, safely (#1505). And when a recent vault's folder holds nothing but `.slate`, Open Recent says so in observable terms rather than opening an empty vault (WD7).

## Design

**#1516 (core).** In `translate`'s per-path arm (`:661-665`), only a **non-rename** modify of an existing directory is dropped: the new guard matches `EventKind::Modify(ModifyKind::Any | ModifyKind::Data(_) | ModifyKind::Metadata(_) | ModifyKind::Other)` **and never `ModifyKind::Name(_)`**, and drops the event when `std::fs::symlink_metadata(path).map(|m| m.is_dir()).unwrap_or(false)`. Every `Name` variant — `From`, `To`, `Any`, and a `Both` the `:644-650` arm did not take because one side is hidden or outside — still becomes `Modified` for a visible directory, so a one-sided or partially visible folder rename still starts its rescan. `Create`, `Remove`, root changes and a `Modify` whose path is missing (the stat errs) are untouched, so the synthetic tests over the non-existent `root()` keep passing. The stat runs on the coalescer thread (one `symlink_metadata` per event, the same cost class as `classify`'s `long_spelling`).

**#1508 (WD5) — an in-vault export is observed, confirmed by the app, and published under that observation.** The non-Markdown question is settled first, by a core fact: `save_text_on_a_non_markdown_path` in `crates/slate-core/src/session/tests/save.rs` pins whether `save_text("export.csv", text, Some(hash))` is accepted, and that with `Some(hash)` it refuses a destination rewritten on disk that no scan has reindexed. **#1505 (WD6) — the safe prune: a worker proves absence; the dispatcher commits and publishes in one turn.**

- *The candidates.* `LoadDirectoryLevel` returns, for a complete level (`!truncated` and the provider page not truncated), `StalePinnedPaths` (a new member of `DirectoryLevel`): the pins of `ordering.Pinned` — the dispatcher's copy the fetch was given, never `_pinned`, which a worker must not read — whose `ParentPath == parentPath` and that are not among the listed paths.
- *Start, on the dispatcher, after the level publishes.* New `private void PruneStalePins(string folder, IReadOnlyCollection<string> stale)` returns at once when `_settingsStore` is null, `_settingsStore.ReadOnlyReason is not null`, `_pinsBehindFile`, the folder is in the per-session `_prunedFolders` (new ordinal `HashSet<string>`) or a prune for it is in flight (new `_pruningFolders`); the candidates are `stale` still in `_pinned`, deduplicated and capped at `SidebarSettingsStore.MaxPinsPerFolder`. It captures `int generation = _pinGeneration` (new `int`, incremented by every write to `_pinned`: `PinSelected`, `UnpinSelected`, `UnpinAllInFolder`, `AdoptSettings`, `TransformStoredPaths`, the constructor's journal replay and the prune's own publication), marks the folder in flight and runs the probe through new constructor parameter `Func<Action, CancellationToken, Task>? pinPruneWorker = null` (the `importWorker` shape; default `Task.Run`).
- *The probe, on the worker — the disk only.* **Absence is proved by an error-aware probe**, new `internal static class VaultAbsence` (`VaultAbsence.cs`) with new `internal static IReadOnlySet<string> AbsentAmong(string vaultRoot, string folder, IReadOnlyCollection<string> relatives)`: walk `folder`'s components from the vault root downward (never statting a candidate leaf first); for each existing component read its attributes (`File.GetAttributes`, which throws on access and I/O errors — any exception means nothing is definitely absent: the empty set); the empty set when any component is a reparse point; when a component of `folder` is itself missing, every candidate is absent **only** if that component's parent is a plain directory whose `Directory.EnumerateFileSystemEntries` succeeded and does not contain the missing name; otherwise one enumeration of `folder`, and a candidate is absent **only** when that enumeration succeeded and does not contain its name (ordinal-ignore-case on NTFS). One ancestor walk and at most one enumeration per call, whatever the number of candidates. New `internal static bool IsDefinitelyAbsent(string vaultRoot, string relative)` = `AbsentAmong(vaultRoot, ParentPath(relative), [relative]).Count == 1`. Inaccessible, erroring or reparse-crossing candidates are kept. The worker touches neither `_pinned` nor `_settingsStore`; it posts its proven set to the tree's UI context (`_treeUiContext`, as the level publication does).
- *Commit and publication, on the dispatcher, in one synchronous turn.* New `private void CommitStalePinPrune(string folder, int generation, IReadOnlySet<string> proven)` clears the folder's in-flight mark, then:
  1. if `_pinGeneration != generation` (a pin edit since the capture), the store is now read-only, or `_pinsBehindFile` is now true: **nothing is written**, memory is untouched and the folder stays eligible (the next complete fetch retries);
  2. otherwise `IReadOnlySet<string> removed = _settingsStore.PruneStalePins(folder, [.. proven.Where(_pinned.Contains)], names => VaultAbsence.AbsentAmong(_vaultRoot, folder, names))` — new `internal IReadOnlySet<string> SidebarSettingsStore.PruneStalePins(string folder, IReadOnlyCollection<string> candidates, Func<IReadOnlyCollection<string>, IReadOnlySet<string>> absentAmong)`, which runs inside `Update`'s locked mutation (`:246-280`, after it re-reads the file under `sidebar.json.lock`) and removes only the candidates still present in the file's pins for `folder` **and in `absentAmong` evaluated at that moment, under the lock** (the probe runs again, as mac re-checks ENOENT at mutation time), returning exactly what it removed;
  3. then, in the same turn with no await or post in between: new test seam `internal Action? StalePinCommitForTests` is invoked, `_pinned.ExceptWith(removed)`, `_pinGeneration++` when `removed` is not empty, and the folder joins `_prunedFolders` only when the store removed something.
  A failed commit (`IOException`, `UnauthorizedAccessException`, `InvalidOperationException`; a blocked file sets the store's `ReadOnlyReason` as any write does) changes nothing in memory, is logged as `HostDiagnosticEvent.SidebarPinsPersistFailed`, is not spoken and leaves the folder eligible; `_pinsBehindFile` is not set, because the file still holds memory's last landed pins.
- *Why the commit is on the dispatcher, not the worker.* `PersistPins` writes the whole `_pinned` set, and every pin edit runs on the dispatcher. A worker that removed candidates from `sidebar.json` before the dispatcher checked `_pinGeneration` would leave the file without a pin memory still holds whenever an edit landed between the capture and that check — the discarded publication keeps it in `_pinned`, and the next `PersistPins` writes it back. A worker-side `Update` would also overlap the dispatcher's own writes on the one store (`OpenExclusiveLock` is `FileShare.None` with no retry, so that pin edit's save would fail as a sharing violation) and race the store's unsynchronised `_root`. On the dispatcher the generation check, the locked mutation and the memory removal form one turn that no pin edit can enter: after every commit the file's pins and `_pinned` agree, so no later `PersistPins` can bring a pruned pin back, and every `sidebar.json` write stays on one thread as today. The dispatcher's cost is the under-lock re-probe — one ancestor walk and one enumeration of a folder whose level was complete (at most `MaxMaterializedDirectoryItems` = 5,000 indexed children, `FilesSidebarViewModel.cs:486`) — once per folder per session, the same class as `PersistPins`' own synchronous anchored write with `FlushToDisk`.
- Nothing is spoken. The write journal is not involved (its entries are renames; a prune is idempotent), and no journal entry is carried or settled by a prune.
