# WB-13 — Deleting the focused canvas card seats the next outline row instead of dropping the keys on the window

Issues: Closes #1260. Size S–M. Lanes: windows (+ one FlaUI journey extended). AT: NVDA spot. Wave: W5 (slot 2, then WB-14). Depends on: nothing. Parallel with: WB-10, WB-15. Decision: none. Interlock: plan 43 PR 32 (#1370) edits `Canvas/CanvasOutlineView.cs` too — whichever lands second rebases (§6).

## Goal

In a canvas outline, deleting the focused card — from the card menu or the palette — republishes the outline with a cleared seat; `Rebuild` recreates every row container, the focused one is gone, nothing takes focus, and WPF drops the keys to the window: NVDA says "Slate, window" and the canvas chord Ctrl+Z does nothing until F6 brings the reader back. After this chunk focus lands on the next row in reading order (else the previous, else the outline tree itself), silently, with the unchanged "Deleted … — Ctrl+Z to undo" sentence, and Ctrl+Z works from there — whether the outline held the keys when the delete published or the palette held them and gives them back afterwards. The completion's `TryMarkFocusReturned`, which nothing calls today, marks that one return.

## Design

- **The keys' lineage (new).** `CanvasOutlineView` keeps `private string? _keysRowId`, the node id of the outline row that last held the keyboard focus. A new `_tree.GotKeyboardFocus` handler sets it from `FocusedRow()?.Id` (a connection row has no node and leaves it unchanged). When `_tree.IsKeyboardFocusWithin` turns false, the loss is classified through `CanvasSurfaceView.ClassifyFocusLoss()` — made `internal static` (new visibility, body unchanged) so the outline and its surface classify one way: `ModalOverlay` (a shell overlay such as the palette) and `MenuOpen` **keep** the lineage (layered over the tab; the keys are coming back), `PaneFocus` **clears** it (the reader went elsewhere). A palette opened from row B therefore leaves `_keysRowId == "B"` while it is up, after it is dismissed and until its restore lands.
- **What `Rebuild()` records** before tearing the rows down: `bool keysHere = HasKeyboardFocus`; `string? keysRow = keysHere ? FocusedRow()?.Id : _keysRowId`; the publication's receipt (below); and the previous reading order (`_lastOrder`, the ids of the previous `population.Outline`, kept as a field from the last rebuild). After `ApplySelection()`, if `keysRow` is non-null, `!_byNode.ContainsKey(keysRow)` and `_selectedRow is null`, it chooses the successor S — the first id after `keysRow` in `_lastOrder` present in `_byNode` (a group counts; a connection row never, it has no node), else the last id before it, else none — and lands it **by where the keys are now**:
  - **The outline holds the keys** (`keysHere`: the row was deleted under them — Delete on the row, the card menu once it has closed, or a palette whose restore already landed back on the row): `DeliverFocus(S)`; with no successor, `SelectorFocus.FocusSelectedOrFirstRow(_tree)` (`:589`), the tree itself, which is the surface root the issue names. The delivery runs inside the sync guard (`SeatFocus`), so it seats the shared selection silently and announces nothing; the operation's `CanvasDeleted` is the only utterance.
  - **A shell overlay or a menu holds the keys** (`!keysHere`, the lineage kept — the palette route, whose publication runs inside `CommandPaletteViewModel.cs:838` with the keys in the palette's field, or between `Dismiss` and the posted Input-priority restore): **seat S without taking the keys** — new `private void SeatWithoutKeys(string nodeId)`: inside the `_syncingSelection` guard, `SetSelectedRow(_byNode[nodeId])` and `model.SeatSelectionSilently(nodeId)` (the seat `DeliverFocus` would make; no focus, nothing spoken) — and remember the return, new `private sealed record PendingReturn(string NodeId, CanvasOperationCompletion? Receipt)` in new `private PendingReturn? _pendingReturn`. The keys come back through the palette's own restore: its token is B's removed container, `TryFocus` fails on it, and `RegionFocusGuard.LandInScopesOf` takes it back to the rows it was in, whose own landing `FocusTree` lands on **the seated row S** (R-5 (h)) — one focus move, silent, made by the restore. With no successor nothing is seated and the restore's landing is `FocusTree`'s (`:588-591`). The outline never takes the keys out of an open palette: that move would be read under a palette still on screen, and the restore would stand down for it (`FocusClaimedOutsideThePalette`); the seat is the coordination, so the order of publication and restore does not matter — publication first seats S for the restore to land on; restore first puts the keys back on B, and the publication then finds `keysHere` and delivers S.
  - **Neither** (the lineage was cleared because the keys went to another pane): no landing; the seat stays null (ClearSelection unchanged).
- **Marking the return.** `OutlinePublished` carries the operation's receipt when the publication is a mutation's: new `internal sealed class CanvasOutlinePublishedEventArgs(CanvasOperationCompletion? receipt) : EventArgs` with `internal CanvasOperationCompletion? Receipt { get; }`, raised by `CanvasDocumentViewModel` at the funnel's republish; loads and filters still raise `EventArgs.Empty`, so the event's type (`EventHandler`) and the surface's subscriber (`CanvasSurfaceView.cs:1174`) are unchanged, and `OnOutlinePublished` reads `(e as CanvasOutlinePublishedEventArgs)?.Receipt`. The outline calls `Receipt?.TryMarkFocusReturned()` exactly once per return: at the `DeliverFocus(S)` above when it held the keys; otherwise in `SeatFocus` when it seats `_pendingReturn.NodeId` (the restore's `FocusTree` landing), clearing `_pendingReturn`. `_pendingReturn` is also cleared by the next `Rebuild` and when the lineage clears, so a later, unrelated `FocusTree` never marks it. A retry cannot deliver twice (the receipt's "true exactly once" rule, `CanvasOperationEffects.cs:116-122`).
- **Test seam (new, production never sets it).** `CanvasDocumentViewModel` gains `internal Action<Action>? HoldMutationForTests { get; set; }`; `CanvasDeleteSelection` consults it immediately before `Funnel.Apply`: when set, the apply (with its confirm) is handed to it instead of run. The palette facts use it to place the publication after the palette's dismissal or after its restore.
- The visual board and the table are not changed: the board keeps its focus already (its seat is cleared; the renderer is the one stop, D15), the table's `AccessibleDataGrid` has its own keepers.
- Not changed: `CanvasMutationEffect.ClearSelection` semantics (the operation still resolves the seat to null — the seated successor is the landing's, as `DeliverFocus` already seats, not a new intent; `SeatSelectionSilently` keeps T3's rule), the delete sentence, the context menu (W7-7 PR 10 fixed it), `MainWindow.RestoreFocusAfterPalette`, `RegionFocusGuard`, `SelectorFocus`.
- No owner decision consumed.

## Amended at implementation (2026-10-28)

- **The publication is posted in production.** A workspace's canvas document runs its transaction on the tracked worker and posts `ApplyPublication` afterwards (`CanvasDocumentViewModel` ctor, the funnel's `run`). Only a synchronous document (tests; a workspace without interaction background work) publishes inside `CommandPaletteViewModel.Invoke`. So all three orders the palette facts force are reachable in production, which is why the design keys on where the keys are at the publication and not on the order.
- **The receipt's hand-off.** `CanvasMutationFunnel.Transact` sets `_publishingReceipt` to the operation's receipt immediately before `RefreshAndPublish` (so whichever dispatcher apply first sees the new rows carries it) and withdraws it when nothing was installed; `PublishReady` raises `OutlinePublished` with `CanvasOutlinePublishedEventArgs(Funnel.TakePublishedReceipt())` when one is waiting, else `EventArgs.Empty`. The other three raise sites are unchanged.
- **The lineage keys a connection row by its source node** (the spec said "leaves it unchanged"): a delete of B while B's connection row holds the keys removes that row too, and B's successor is the right landing.
- **No successor while the outline holds the keys** calls `FocusTree()`, not `SelectorFocus.FocusSelectedOrFirstRow(_tree)` directly: with no rows that is the same call (the tree itself), and with rows the lineage did not know (a reload that replaced every row) it lands the first row instead of leaving the bare tree with the keys (R-5).
- **A pending return survives a republish that keeps its successor seated** (the posted apply after a synchronous one); any other rebuild, a model change and a lineage clear drop it.
