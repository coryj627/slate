## Goal

With a combo box's list open, every element UI Automation publishes for a row says where the row is in its list and how long the list is, and says exactly what WPF's own item peer says for that row. That holds for all eleven combo boxes, however their rows are styled, when the list changes while it is open or closed, and after it is closed and opened again. The shell gate scans a list open in each of the three row families and stays clean, and a census holds every combo box to one of those families and to the fact that opens it.

With a combo box's list open inside a sheet, Escape closes the list and leaves the sheet open with the keys on the combo box, and Enter chooses the highlighted row and does nothing else. That holds in the query builder, the dashboard editor, Add property and Bulk rename, as it already does in Settings.

## Design

### The rows

**One tracker for each combo box keeps the two attached properties on every realized row equal to WPF's own answer.** `AutomationProperties.PositionInSet` and `AutomationProperties.SizeOfSet` are set on each row container to `Items.IndexOf(item) + 1` and `Items.Count`, the numbers WPF's item peer computes without them. Both of a row's elements then report the same place. The rule the tracker must keep, and the one every fact below tests: **a stamped row says exactly what WPF's item peer would have said with no stamp.** A stamp that goes stale would make wrong the element NVDA reads today, which is right today (measured: after an insert with stale stamps, a row at 2 of 5 said 1 of 4). So the tracker restamps every realized row on every event that can move a row or change the count, and where WPF's answer is not "index + 1 of count" it removes its stamps and leaves WPF's answer.

1. **`S/ComboBoxRowPlaces.cs`, a new internal sealed class.** The prototype that was measured is kept with this chunk's working notes; the product class has its shape:
   - One instance for each `ComboBox`, held in a `ConditionalWeakTable<ComboBox, ComboBoxRowPlaces>`, holding the combo box weakly. Measured: a tracker does not keep a combo box alive.
   - On attach it subscribes to the combo box's `DropDownOpened`, its `ItemContainerGenerator.StatusChanged` and `((INotifyCollectionChanged)combo.Items).CollectionChanged`, and restamps once.
   - `Restamp`: first, any container it stamped that the generator no longer owns has both properties cleared. Then, if the combo box is grouping or recycles its rows (`VirtualizingPanel.VirtualizationMode` is `Recycling`, virtualizing is on and the rows sit in a `VirtualizingPanel`), it clears both properties on every realized container and stops. Otherwise, for each realized container, it writes the two values, and only where a value differs.
   - `Restamp` is one pass over the items, not one `IndexOf` for each row. It builds a map from each item to its first index under the items' default equality (which is what `ItemCollection.IndexOf` answers, so two equal items both get the first one's place, as WPF gives them), and holds the stamped containers in a `HashSet`. The prototype's `IndexOf` for each row and `List.Exists` for each stamp are quadratic: a saved-query list refreshed by `Clear()` and one `Add` for each query (`S/WorkspaceViewModel.Bases.cs:1600-1604`) restamps once for each `Add` while the dashboard picker stays bound (`S/MainWindow.xaml:4097`), so the product class must not be.
   - `Restamp` never throws into layout. It runs from a class handler for every combo box in the process, so it catches the `InvalidOperationException` a view under `DeferRefresh` gives for `Count` and `IndexOf`, leaves the stamps as they are, and is run again by the `Reset` that ends the deferral. No app code defers a combo box's view today (searched); the guard is for the shared default views of static arrays such as `ConnectionsPhrase.DepthTags` and `AddPropertyViewModel.Kinds`. A hosted fact pins it (fact 2's deferral arm).
   - Clearing uses `ClearValue`, so a row returns to having no local value and WPF's own answer.
2. **The attach, with no per-site edit.** One static `Register()`, guarded to run once in a process (the guard saves a second pair of handlers; a second registration would attach nothing new, because the table hands back the same tracker and the tracker subscribes only in its constructor), registers two class handlers:
   - on `ComboBox` for `FrameworkElement.SizeChangedEvent`: attach the tracker to the sender. Measured in a fresh process on the real shell: this fires for every combo box before its first open (the six in sheets when the sheet is first shown, the DataTemplate ones when their section is added, the code-built `BaseViewPicker`, and stand-ins built as rows 9 to 11 are), and the tracker is attached before the open in every case.
   - on `ComboBoxItem` for `FrameworkElement.SizeChangedEvent`: find the row's combo box (`ItemsControl.ItemsControlFromItemContainer`) and attach if no tracker is attached. This closes the one hole measurement found: a combo box with zero width, height, minimum width and minimum height never raises `SizeChanged`, can still be opened through UI Automation, and its rows went unstamped. A row raises `SizeChanged` once when it is first laid out, inside the open. No app combo box has that shape; the second handler makes "every combo box" true without relying on that. It was not prototyped: fact 6 below is its proof, and if fact 6 is red with it in, stop and tell the principal.
   - `MainWindow`'s constructor calls `ComboBoxRowPlaces.Register()` beside `SelectorFocus.RegisterClickRule()` (`S/MainWindow.xaml.cs:64`), which is the precedent for a process-wide class handler the window registers as it is built. Every combo box in the app is inside that window. A hosted fact that builds a combo box with no shell calls `Register()` itself, as `T/BasesDocumentTests.cs:821` does for the click rule.
   - `T/Censuses/ShellSealAdmissionCensus.cs` reads every `RegisterClassHandler` call and will refuse the two new ones: `PastHandledOffenders` (`:718-752`) reports any class handler whose event is not in `IsKnownNonInput` (`:1544-1546`: `Loaded`, `TextChanged`, `CleanUpVirtualizedItem`) or in a reviewed list, with "registers a class handler for FrameworkElement.SizeChangedEvent". The PR adds `FrameworkElement.SizeChangedEvent` to `IsKnownNonInput`, with a comment that it is a layout event that carries no input, and the census joins the files this chunk edits. `SizeChanged` is a direct event that nothing marks handled, so the product registers without `handledEventsToo`; the measured prototype passed `true` (`prototype-Cb19Tracker.cs.txt:38-43`), which makes no difference for an event no one handles.
3. **When rows are stamped, measured with the prototype.** At a first open the order is the same on every route (Alt+Down, F4, the template's toggle, `IsDropDownOpen = true` in code, UIA `ExpandCollapse.Expand` through the real peer): `DropDownOpened` with 0 rows, `StatusChanged(ContainersGenerated)` with the rows present, where the tracker stamps, then each row's `SizeChanged`. All of it is inside the open, so no dispatcher operation, and so no UI Automation call, starts with a realized row unstamped (0 of every boundary scanned). A combo box in a collapsed sheet has no tracker yet and cannot make rows: setting `IsDropDownOpen` there makes no popup. `IsDropDownOpen = true` before the combo box is loaded is deferred by WPF until it loads, after `SizeChanged`.
4. **What the tracker was measured to keep**, each as a twin run against an untracked combo box with the item peers compared at every step: first open, close and reopen; insert, remove, move, replace, clear, a view sort, a view filter and an `ItemsSource` swap, each while open, while closed after an earlier open, and before the first open (24 runs); a collapsed row (WPF counts it, and so does the stamp); two equal items (both say 1 of n, as WPF does); a changed selection; the combo box taken out of its parent and put back with changes in between; the combo box moved to another parent; grouping switched on and off (the stamps are cleared, the popup's tree is item peers under grouping and passes with no stamps, and ungrouped rows are restamped); standard virtualization (stamps follow realization); 300 rows. No step differed from WPF's answer. **Not measured: a runtime theme change.** `ThemeManager.ApplyResources` (`S/ThemeManager.cs:348-369`) swaps in new Fluent and Slate dictionary instances on a theme, contrast, accent or text-scale change, which can be made from `SettingsTheme` itself, so a combo box's template and its items host are applied again and the row templates arrive again by `DynamicResource` (`S/ClassicRows.cs:47`). By reading WPF, a new items host makes the generator drop and regenerate its containers, which raises `StatusChanged` and so a restamp. Fact 2 gains the arms that measure it.
5. **The one shape it leaves as it is today: a recycling combo box.** With recycling forced, the tracker stamps nothing and the item peers stay right, but the popup's rows read -1 again. No app combo box recycles, and the census refuses one that would (below).
6. **Cost, measured with the prototype's quadratic restamp:** for 300 realized rows a restamp that writes nothing takes 0.5 to 1.1 ms and one that rewrites all 600 values 0.9 to 1.6 ms; a first open restamps three times. The product's one-pass restamp is no slower; the implementer measures a 300-row `Clear()` and refill of an opened list's source and records it in the PR body.
7. **Speech.** By reading the runtime: the two properties have no changed callback and no coercion, and `AutomationPeer.UpdateSubtree` raises property-changed events for item status, name, offscreen and enabled only. So writing them should make a screen reader say nothing new. That is not measured; the NVDA spot check listens for it.

**Rejected.**

- *Stamping once as a list opens* (the reading's shape). There is no class-level "list opened" event (`DropDownOpened` is a CLR event; `Loaded` class handlers fired 0 times for these combo boxes), no rows exist at `DropDownOpened` on a first open, and a stamp that is not kept goes stale.
- *A peer override that computes live.* It needs a `ComboBoxItem` subclass and a `ComboBox` subclass (`OnCreateAutomationPeer` is `ListBoxItem`'s and `GetContainerForItemOverride` is `ComboBox`'s), so eleven sites change type, in files plan §6 gives to other chunks, and a subclass does not pick up Fluent's implicit style (the trap of #1767). It could not go stale, which is its merit; the tracker's facts are the answer to that.
- *An opt-in at each site.* Not needed: the class handlers reach all eleven, and a twelfth is covered the day it is added.
- *Waiving the popup's rows in the gate.* The focused element is right in every family, but the popup's copy is what a client that walks or hit-tests the popup reaches, and the issues ask that rows report their place.

### The Escape and Enter find

**Each of the four tunnelling handlers stands down when the key comes from inside a combo box whose list is open, and so does the window's import cancel.** One private static helper in `MainWindow`, `OpenComboListOwnsKey(KeyEventArgs e)`, walks from `e.OriginalSource` with the existing `ParentOf` (`S/MainWindow.ShellRegions.cs:1386-1389`, the walk `MenuModeOwnsEscape` already uses: the visual parent, and the logical parent where the visual tree ends, which is the hop out of the popup) and answers whether it meets a `ComboBox` with `IsDropDownOpen`. The walk only climbs ancestors, so it cannot meet a sibling's open list. Each of the four handlers returns at once, leaving the event unhandled, when it answers true, and the import-cancel condition at `S/MainWindow.xaml.cs:1444-1450` gains `&& !OpenComboListOwnsKey(e)` beside `MenuModeOwnsEscape(e)`. The combo box then does what it does everywhere else: Escape closes the list, and Enter chooses the highlighted row and closes the list. With no list open every handler does exactly what it does today. The import route is found and fixed here: it is small by `AGENTS.md`'s rule (`MainWindow.xaml.cs` is already in the diff and the helper is in the same partial class), with its own red fact (fact 13).

Measured with this change as an experiment on all four sheets, then reverted: Escape closes only the list and leaves the keys on the combo box; a second Escape closes the sheet; Enter chooses the highlighted row and adds, previews and applies nothing; a second Enter with the list closed does what it does today. 538 existing facts passed with it in (the sheet, modal surface, keyboard fence and landing classes, and the SheetFence, FocusIntegrityManifest, RegionGuard, SelectorLanding and SaveChainAdmission censuses). No test names any of the four handlers.

**Why not the Settings sheet's shape here: measured.** The lead's first preference was the Settings sheet's shape, a bubbling `KeyDown`. A bubbling handler is not called for a key a control has already handled, so step 0's third round ran the four sheets three ways in the hosted shell, through the real handlers: today (T), with the four overlays' `PreviewKeyDown=` changed to `KeyDown=` and the handler code unchanged (B), and with the stand-down (S). For each sheet it focused every keyboard-focusable control in the overlay (116 control and key cases, focus confirmed on the intended control in every one) and pressed Escape and Enter, then ran each combo box with its list open (14 cases). Results:

- **B misses one key from one control: Enter in Bulk rename's preview grid.** WPF's `DataGrid` handles Enter whenever a cell is current, so the sheet's handler is never called. Today, and with S, Enter on any grid cell runs Preview again, keeps the current cell and speaks the rename summary. With B, Enter there runs no Preview and says nothing; with two rows it moves the current cell down one row. Escape from the grid closes the sheet in all three, because the grid does not take Escape when no cell is being edited.
- **Buttons** handle Enter themselves (they click) in all three states; today's handlers already leave a Button source alone, so B and S equal T there.
- **Every other control** (the text boxes, the closed combo boxes, two focusable text blocks, the dashboard's section row) reached the overlay with both keys unhandled, and B and S equal T.
- **A combo box with its list open:** B and S give the same result in all 14 cases (Escape closes only the list; Enter chooses the row and runs nothing), and both differ from T.
- **S differs from T in 11 rows, every one a combo box with its list open.** No other control changes.
- Apply never runs from a sheet's handler in any state. Enter on the Apply button runs Apply, as its own activation, in all three.

So the bubbling shape would change what Enter does in Bulk rename's grid, and the stand-down changes nothing but the open list.
