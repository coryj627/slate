## Goal

On Windows, a rename that changes only the case of a file's or a folder's name never reports success while the volume keeps the old spelling. Core reads the stored spelling back after the kernel call. Where the volume kept the old one, the rename fails with core's sentence, the index, the links, the tabs and the stored paths stay as they were, and the Files sidebar says why with the keys still in the rename field. The lane's weak-volume job runs the case-only fact it has skipped by name since #1930, on FAT32 and exFAT VHDs.

## Design

**Where the refusal is decided: in core's provider, after the kernel call, by reading the name back.** Not before the call from the volume's file-system name. Reasons: the one recorded observation is an Insider build, so a rule keyed on `FAT32` or `exFAT` could refuse a rename the volume would have made and say a sentence that is false there; the read-back needs no list of file systems and also covers a FAT volume reached some other way; and NTFS is untouched because it applies the rename, so the read-back finds the requested spelling. The check runs only when `destination_is_source` is true, so an ordinary rename, a move, a save and every other volume operation gain no call.

1. **`C/vault/windows_entry.rs`, a new helper beside `entry_exists`:** `pub(super) fn stored_name(parent: &fs::File, name: &OsStr) -> io::Result<OsString>`. It opens the entry `name` in `parent` as itself, with attribute access and full sharing (the open `entry_exists` makes, `:474-487`), and returns the final component of `super::trash_handoff::final_path_any(&entry)` (`C/vault/trash_handoff.rs:468-471`). This is the read `canonical_path` already trusts for the stored spelling beneath a held root (`C/vault/fs_root.rs:1049-1054`), so the check and the index's own binding read the same thing. **Unverified:** that this read reports the on-disk spelling on FAT32 and exFAT, straight after a rename the volume ignored and after one it applied. Step 0 (M2) measures it against the folder listing. The red team's correction: M2 must measure what production reads. In `rename_beneath_root` the read-back runs while `source`, the renamed entry's own handle, is still open: it is the handle `rename_into` is called on (`:637`) and it lives to the end of the function. The provider's `canonical_path`, read after `rename` has returned and closed its handles, is a different moment, and on FAT the two can disagree. So fact 5 makes the read with the renamed handle open. Fallback if it does not: read the name from the listing (`windows_entry::reopen` with `sys::LIST_ACCESS`, then `sys::read_dir_entries`, `C/vault/fs_root_windows.rs:430`), which needs list access on the folder and reads the whole folder.
2. **`C/vault/fs.rs`, the Windows `rename_beneath_root`.** The match at `:637-654` keeps its arms. Its result is bound, an error returns as today, and then, only when `destination_is_source`:

   ```rust
   let stored = windows_entry::stored_name(destination_parent.handle(), to_leaf)
       .map_err(|error| destination_parent.failed(error))?;
   if stored.as_os_str() != to_leaf {
       return Err(VaultError::InvalidArgument {
           message: crate::a11y::case_only_rename_refused(
               &stored.to_string_lossy(),
               &to_leaf.to_string_lossy(),
           ),
       });
   }
   ```

   The comparison is exact. A read-back that fails returns its own error; the rename is never reported as done on a spelling core could not read. The method's doc comment gains two sentences for the read-back and #1727.

   **A refused rename records its echoes** (the red team's correction 2). The kernel call succeeded, so the volume may have reported a change, and `recorded` (`:323-332`) writes the ledger only on `Ok`. Without an echo, an event the watcher saw for either name is not dropped as Slate's own (`C/session/watch.rs:453-456` touches both paths of a rename event; `:706-711` keeps every path that is not an echo), and the session is called for them as an outside change. So when the kernel call succeeded and the read-back refused, `FsVaultProvider::rename` (`:2235-2238`) records the echoes for `[from, to]` before it returns the refusal. How the refusal is told apart from a kernel error there is the implementer's choice; the sentence is not parsed. A rename the kernel itself refused still records nothing. Whether the watcher sees any event on a FAT32 or exFAT volume that ignored the rename is **unverified**: the gated fact and the probe note it on the real volumes.

   **A read-back that fails is a residual** (correction 7). If the rename was applied and the read then fails (an outside delete or rename between the two calls, or a filter that fails the attribute open), the disk holds the new spelling and the index the old, and the reader hears the read's own error. The PR states it as a residual and puts one line on #1955, unless an existing sentence already fits a report whose outcome is unknown.

   **The identity inverse** (`windows_entry::rename`, `:1022-1051`) is not changed and has no read-back (correction 8). It is the route of undo and redo (`ExecuteUndoStep`, `S/FilesSidebarViewModel.FileManagement.cs:382-383` and `:404-405`). By reading it cannot be reached on FAT32 or exFAT: it reads the source's `FileIdInfo` identity first (`:1029`, `identity` at `:985-1004`) and returns the query's error where the volume does not answer it. Not run. The PR names it as a residual.
