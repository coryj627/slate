## Design

1. **A panic fails its diagram alone.** Both panic setters go: the store at `D:647` and the block at `D:771-776`. The arm at `D:646-651` returns `RenderError::Failed` with the new sentence and drops the payload. Nothing else changes for the next diagram: it is attempted. An abandoned render that panics has no caller; it says nothing, sets nothing, and still releases its slot (`RenderSlot`, `D:697-705`). The default panic hook already prints the panic's own message and place to stderr, and that is not changed.

2. **The session-long short-circuit is kept for one case only: an upstream error that names a poisoned lock.** The rule has two parts, and both must hold:
   - **By type: the error is not the renderer's parse diagnosis.** An error that is a `mermaid_rs_renderer::ParseError` (re-exported at `U/lib.rs:108`) is about this diagram's source and may quote it, so it never sets the flag, whatever its text. The check is made where the typed error exists, on the render thread, on the `anyhow::Error` that `render` returns, before any text is taken from it: `e.chain().any(|c| c.is::<mermaid_rs_renderer::ParseError>())`. The red team's correction: the whole chain is read, not the outermost error, so a parse diagnosis a later version wraps in a context is still a parse diagnosis. `chain` and `is` are methods on the value, so `anyhow` does not become a direct dependency. M1 measured that `is::<ParseError>()` is true through the `?` in `render_with_options` (`U/lib.rs:222-227`); fact 4 pins it. In 0.3.1 that `?` is the only fallible step, so every upstream error today is a `ParseError`, and the kept branch cannot fire with 0.3.1. It is the guard for a later 0.3.x that returns a lock error, as CD18 intends.
   - **By text: it names a poisoned lock.** A new `names_a_poisoned_lock(text: &str) -> bool` is true when the text contains `PoisonError` or `poisoned lock`, case-sensitive. Those are the two renderings of `std::sync::PoisonError`: its `Debug` is `PoisonError { .. }` and its `Display` is "poisoned lock: another task failed inside". Both were measured on rustc 1.99.1 ("Step 0, as run"); fact 6 pins both against a really poisoned `Mutex`. The bare substring "poison" is no longer matched. `TryLockError::Poisoned` prints `Poisoned(..)` in `Debug`, which neither literal matches; it is not added until a route is shown by which a try-lock's error text reaches Slate.
   - **Which text is tested** (the red team's correction 1). Not `e.to_string()`. An `anyhow::Error`'s `Display` shows only its outermost context, so a lock error wrapped as `.context("measuring label text")` prints only "measuring label text" and would never match. The flag is computed from the whole chain: `format!("{e:#}")`, or each link of `e.chain()`. `e.to_string()` stays as the reason the reader is shown, as today (`D:769`). 0.3.1 wraps nothing in a context; the rule is for the later version the kept branch guards against. Fact 5b pins it.
   - **Why this one means the renderer cannot be used again.** A std lock stays poisoned until its owner calls `Mutex::clear_poison`, and an error that reports the poison comes from a renderer that did not clear it or work around it. Every later render that takes that lock would fail the same way, so one sentence that says so is better than the same opaque error on every diagram.
   - **Shape.** The render thread's error carries the reason shown (`to_string()`), whether its chain names a poisoned lock, and whether it was a parse diagnosis, in place of the bare `String` in `RenderThreadOutcome` (`D:709`) and `RendererError::Upstream` (`D:668`). The `#[cfg(test)]` seam's signature stays `Fn(&str) -> Result<String, String>`: a seam's `Err` is carried as "not a parse diagnosis" and its one text is the whole chain, so a fact can stand in for a lock error by its text. The decision itself is a pure function of the chain's texts and the parse answer, so fact 5b can give it a two-link chain without building an `anyhow::Error`. The implementer picks the type's name.
   - **A lock error from an abandoned render** is dropped with its result, as every abandoned outcome is. The next waited-on render meets the same error and sets the flag. Nothing is added for it.
   - **The "unsupported" classification at `D:640-641` keeps reading the text** for every upstream error, as today. Its defect is deferred.

3. **The sentences.**
   - New, verbatim: **"Diagram not drawn: the renderer failed on this diagram. The source follows."** It is a private constant in `diagram.rs` beside `render_time_exceeded_message`, with a doc comment saying both hosts show it verbatim as the failed state's reason. Core owns the copy. It is not a new form of `render_time_exceeded_message`: no host needs to recognise it, and that would touch `lib.rs`'s doc comment.
   - "The source follows." is true on Windows (`ApplyFailureShape`, the source run after the reason) and on the Mac (`failureFallback`, the source under the reason), as it is for the three budget sentences that already end with it.
   - **The two session-long sentences stay byte for byte** (`D:610-615`, `D:634-639`). After this chunk the first is said on the diagram whose render returned the lock error, and the second on every later diagram in the process. No input is known to reach either with 0.3.1; the seam does. Plan §8 and #1954 say "the session-long sentence goes". What is delivered is narrower and is what CD18 asked for: the sentence no longer follows a panic, or a diagram whose text holds "poison". It stays in core behind the narrowed check. Open question 2 puts the wording of the ledger line, and whether these two sentences should be reworded, to the lead.

4. **Transient or not (WB-20, plan 44 §3.1).** WB-20's rule is that a transient refusal, core's "busy" render or the host's "image-busy" decode, is shown and never landed, so the next refresh retries it. Neither sentence here is a refusal. A panic is a failure of this diagram, and a poisoned lock does not clear. Both stay `RenderError::Failed`, `transient: false`: core caches the block and Windows lands it, as it does today for the old sentences. `RenderError::Busy` and the "busy" path are not touched. The Windows fact asserts the landing.

5. **The test-fault seam.** Two environment variables, read on the render thread just before the real render (after the `#[cfg(test)]` seam at `D:765-768`, before `D:769`), so a forced fault takes the same channel, counters and `catch_unwind` as a real one:
   - `SLATE_TEST_FAULT_DIAGRAM_PANIC`: when set, not empty, and the diagram's source contains its value, the render panics with the message "test fault: injected diagram render panic".
   - `SLATE_TEST_FAULT_DIAGRAM_POISON`: when set, not empty, and the source contains its value, the render returns the upstream error text "test fault: poisoned lock: another task failed inside", carried as "not a parse diagnosis".
   - The value is a substring of the source, the discipline of the path seams (`session.rs:8952-8954`), so one diagram in a note can be named and the next left alone. An unset or empty variable does nothing. The decision is a pure function of the two values and the source, with a thin reader of the environment over it, so "inert" has a fact with no environment write.
   - The seam is compiled into every build, as core's other `SLATE_TEST_*` seams are. Its doc comment says three things: it is for field passes and tests; a fact sets a value no other fixture's source contains; and **no hosted Windows or Mac fact may set `SLATE_TEST_FAULT_DIAGRAM_POISON`**, because the flag is process-wide and has no reset outside core's test build, so it would fail every diagram fact that ran after it in the same test host.
   - In core's tests the two variables are written only under `renderer_test_guard`, through a small guard in `diagram.rs`'s test module that removes them when it drops, on return and while unwinding. They are not added to `FAULT_VARIABLES`.
   - **How the guard writes them** (the red team's correction 3). The two names are product constants in `diagram.rs`, which the seam's reader uses. The test guard takes the name as a parameter and calls `set_var(name, value)`, never with a literal. The census `no_test_sets_a_fault_variable_outside_the_guard` (`crates/slate-core/src/session/tests/fault_guard.rs:100-150`) reads every source under `src` for `set_var(` followed by a literal that starts `"SLATE_TEST_`, and passes over only `session/tests/common.rs`, so a literal in `diagram.rs` fails it. `fault_guard()` is `pub(super)` in `session::tests::common` (`common.rs:114`), so `diagram.rs` cannot take that guard. The census reads literal names only, by its own comment, so the parameter form passes it; the renderer test lock is what serializes the writes.

6. **Comments corrected in `diagram.rs`:** the flag's (`:516-519`), `try_render_mermaid`'s audit paragraph (`:600-603`), and the note in the render thread (`:772-774`, which goes with its block). Each says what is now true: the flag is set only by an upstream error that names a poisoned lock; mermaid-rs-renderer 0.3.1 takes its measurer lock per measurement and falls back when it is poisoned, so a panic disables nothing.
